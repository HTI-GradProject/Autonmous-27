1. Overview and Hardware Context

This report documents the design of the SLAM (Simultaneous Localization and Mapping) module for a Mars-analog rover competing in the European Rover Challenge (ERC). The SLAM module is responsible for producing a continuous, drift-corrected pose estimate of the rover, which downstream navigation and the existing perception module rely on.

Hardware Available to the SLAM Module:

  • Wheel encoders: 4x wheel encoders on independently driven wheels, used for dead-reckoning odometry.
  • BNO IMU: providing orientation (quaternion), angular velocity, and linear acceleration.
  • RealSense camera: an Intel RealSense D4xx-series RGB-D camera, used both for visual odometry input and for detecting ArUco markers.
  • Compute: NVIDIA Jetson Orin Nano — this constrains which SLAM/VO algorithms are practical to run in real time.

Upstream context: a perception module is already implemented and publishes a costmap with obstacle features and obstacle markers. The SLAM module does not duplicate this — its job is to provide the accurate, drift-corrected coordinate frame (map → odom → base_link) that the perception output and the navigation stack are expressed in.

Additional input: the competition environment includes ArUco markers at known, surveyed world coordinates. These are used as periodic absolute corrections to counteract the drift that is unavoidable in wheel- and vision-based odometry alone.

3. Submodule Breakdown

3.1 Sensor / Driver Layer

Raw sensor nodes, each publishing at native rate with hardware timestamps rather than arrival timestamps. Two things must be correct before anything downstream is trustworthy:

  • Time sync: Time synchronization between IMU and camera streams — even a 50 ms skew visibly corrupts visual odometry.
  • Extrinsic calibration: camera-to-IMU, camera-to-base_link, and wheel radius/wheelbase must be calibrated once (e.g. with Kalibr) before use.

3.2 Per-Sensor Filtering

Each sensor is filtered before it reaches fusion:

  • Wheel encoders: compare per-wheel speed against IMU-derived turn rate; disagreement indicates slip, and that sample is down-weighted or discarded. A low-pass filter also removes tick-count quantization noise at low speed.
  • IMU: low-pass filter on linear acceleration to remove chassis vibration; periodic gyro bias re-zeroing during known-stationary moments; outlier/spike rejection for bumps on rocky terrain.
  • RealSense depth: RealSense SDK post-processing chain — decimation, spatial, temporal, and hole-filling filters, plus hard min/max depth range clipping. Outdoor sunlight degrades IR-based depth accuracy.

3.3 Fuzzy Adaptive Weighting

Fixed-covariance fusion assumes constant sensor trust at all times, which does not match reality on loose or rocky terrain. This stage computes real-time indicators — a wheel slip score and a vibration/innovation magnitude — and uses them to dynamically scale how much each sensor is trusted.

Recommended first implementation: a simple heuristic threshold-based weighting (e.g. reduce wheel odometry trust proportionally to a computed slip score), rather than a full fuzzy inference engine.

3.4 RTAB-Map (Odometry + Fusion + Mapping Backend)

RTAB-Map is the core SLAM engine. It accepts wheel odometry, IMU, and RGB-D input directly, performs the sensor fusion internally, builds and maintains the pose graph, and performs loop closure via visual place recognition.

Alternative Odometry Front-Ends Considered:

  • ORB-SLAM3: more accurate on paper, but a harder research codebase to build, tune, and debug on ARM/Jetson.
  • VINS-Fusion / Open-VINS: strong VIO but assumes tight stereo+IMU integration and preintegration knowledge.
  • RTAB-Map (chosen): ROS2-native, includes pose graph and loop closure out of the box, and is far easier to debug.

3.5 ArUco Correction (Filtered and Gated)

Pipeline: detect marker → estimate pose → look up known coordinate → invert transform chain

  • Subpixel corner refinement improves pose accuracy over raw corner detection.
  • Reprojection error check: reject detections above an error threshold.
  • Distance / angle gating: discard detections beyond a maximum usable distance.
  • Temporal consistency check: only accept a correction seen consistently across consecutive frames.
  • Mahalanobis distance gating: compare against the current pose uncertainty. A correction that disagrees wildly with the current belief is rejected or down-weighted.

3.6 Output

The module publishes:

  • /odom: continuous, high-rate pose in the odom frame.
  • map → odom transform: periodically corrected by RTAB-Map's graph and ArUco.
  • /slam/pose: best current global pose estimate, in the map frame.
  • Full TF tree: map → odom → base_link → {camera, imu, wheels}.

4. Integration with the Perception Module

The perception module already publishes a costmap with obstacle features and obstacle markers, in a local (base_link or odom) frame. Once the SLAM module publishes a stable, drift-corrected map → odom transform, the navigation stack can transform perception's costmap into the map frame for globally consistent path planning. The SLAM module is not responsible for rebuilding obstacle maps.

5. Future Work: Error-State / Iterated Kalman Filter

RTAB-Map's internal fusion is not a Kalman filter, so this is worth planning for as a second iteration if ArUco corrections do not converge cleanly:

  • Iterated EKF (IEKF): re-linearizes the measurement model around the updated estimate — more accurate for nonlinear measurements.
  • Error-state formulation (ESKF): estimates the error between an IMU-propagated nominal state and the true state, avoiding quaternion singularities.

7. Open Decisions

  • Marker density: How many ArUco markers will realistically be visible during the autonomous task, and how far apart?
  • Fuzzy weighting fidelity: whether to implement the fuzzy weighting as a heuristic (recommended for v1) or a formal fuzzy inference system.
  • Outdoor validation: test RTAB-Map's RGB-D odometry and the RealSense depth filters on actual outdoor, Mars-analog terrain early.
