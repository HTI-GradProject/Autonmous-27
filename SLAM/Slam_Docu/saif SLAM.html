1. Core Concept

Instead of relying on a single visual SLAM node that handles everything, this architecture divides the localization system into two complementary pipelines:

  • Local State Estimation (The "Copilot"): Uses a dedicated Extended Kalman Filter (EKF) from robot_localization to fuse high-speed sensor data (IMU and Wheel Encoders). It provides a fast, smooth, local odometry loop for navigation control.
  • Global Drift Correction (The "Navigator"): Uses RTAB-Map to run visual loop closures and align the map. It does not control local movements directly; instead, it outputs a slow, global transform offset ($map \rightarrow odom$) when it sees familiar rocks or ArUco landmarks.

1.5. Deep Dive: TF Trees & Coordinate Frames

What is a Coordinate Frame?

A coordinate frame is a local 3D workspace (with X, Y, Z axes). To know where the rover's camera is, or where a rock is, we must describe their coordinates relative to a specific reference point. In ROS, we keep track of these relationships using a TF Tree (Transform Tree).

What does the Arrow ($A \rightarrow B$) mean?

In a TF Tree, the arrow is a parent-child relationship. An arrow from **Parent $\rightarrow$ Child** means: "Where is Child relative to Parent?"

For example, if `base_link` $\rightarrow$ `camera` is a transform of [X=0.2m, Y=0m, Z=0.3m], it means the camera is physically located 20cm in front and 30cm above the center of the rover.

Detailed Breakdown of the Two Crucial Transforms

1. The Local Link: odom → base_link

  • What it means: "Where is the physical center of the rover (`base_link`) relative to the place we turned it on (`odom`)?"
  • How it is calculated: Calculated at a high rate (100 Hz) by the EKF node (`robot_localization`) fusing wheel ticks and IMU data.
  • Why we use it: Since it is calculated using physical sensors at high speed, it has **zero latency** and **no coordinate jumps**. This is crucial for local steering controllers (like MPPI), which would crash if the coordinates suddenly jumped.
  • The Catch: It is not globally corrected. If wheels slip, the position starts to drift over time.

2. The Global Link: map → odom

  • What it means: "Where is our starting point (`odom`) located in the actual static world map (`map`)?"
  • How it is calculated: Calculated at a lower rate (1–5 Hz) by the visual SLAM node (RTAB-Map) using camera feature matching and ArUco markers.
  • Why we use it: It serves as a **global offset correction**. If the EKF drifts by 50cm, RTAB-Map notices this drift by looking at landmarks and adjusts the starting point coordinate offset. This updates the robot's global position without affecting the smooth EKF calculations.
  • The Catch: It can have sudden coordinate "jumps" when a drift correction occurs, making it unsuitable for direct steering control, but perfect for global path planning.

How the Path Planner uses the TF Tree

The Global Path Planner needs to draw a route from the robot's current position to a goal on the map. To do this, it requests the transform from map → base_link. ROS automatically calculates this by tracing the TF tree parent-to-child chain:

(map → odom) + (odom → base_link) = map → base_link

Are /odom and /map the only outputs we need?

No. While `/odom` and `/map` are the primary topics you see in ROS 2, they cannot work together without the **Coordinate Transform Tree (TF Tree)**.

  • Why /odom alone isn't enough: It only tracks local movement relative to where the rover started. Over time, wheel slip causes this coordinate frame to drift. The global path planner doesn't know where the obstacles on the map are relative to `/odom` directly.
  • Why /map alone isn't enough: The global map is static. It tells you where the rocks are, but it does not tell you where the robot is in real-time.
  • The Glue (TF Transforms): To navigate, Nav2 must know where the robot is *on the map*. The SLAM module provides this by publishing the map → odom transform link. This link bridges the gap, allowing the planner to transform the high-speed local pose (`odom → base_link`) into the global coordinate system (`map → base_link`).

4.5. Detailed Component & Topic Breakdown

A. The Core Processing Blocks

1. robot_localization (EKF Node)

What it does: Fuses linear velocity from the wheels and orientation values from the IMU using an Extended Kalman Filter to estimate smooth coordinates.

Where to use it: Used as the local state estimator node to broadcast `/odometry/filtered` and the local odom → base_link transform link.

How to get it: Install via apt: sudo apt install ros-jazzy-robot-localization.

How to do it (Brief Implementation): Create an ekf.yaml file (see Section 7) selecting wheel velocity (X, Y) and IMU orientation/yaw rate. Start the ekf_node in your launch file, referencing this parameter configuration.

2. RTAB-Map SLAM Node

What it does: Extracts visual features from the camera, builds a database of mapped areas, runs loop-closure detection, and calculates the global shift offset to correct odometry drift.

Where to use it: Used as the mapping backend to output the static `/map` and broadcast the global map → odom transform offset.

How to get it: Install via apt: sudo apt install ros-jazzy-rtabmap-ros.

How to do it (Brief Implementation): Configure the main rtabmap node in your launch file. Set the publish_tf parameter to true and map the EKF output (`/odometry/filtered`) to its input odometry topic. Enable loop closures via parameters.

3. ArUco Detector Node

What it does: Processes the raw camera image to identify marker IDs and calculates their camera-relative 3D pose (X, Y, Z, Pitch, Yaw, Roll).

Where to use it: Used as a perception helper node to feed absolute landmark corrections to RTAB-Map.

How to get it: Written as a custom Python node utilizing standard OpenCV library modules (opencv-python-headless).

How to do it (Brief Implementation): Write a Python script subscribing to `/camera/color/image_raw`. Use cv2.aruco.detectMarkers() to locate corners, run cv2.solvePnP() against camera calibration parameters, and publish the marker's 3D pose relative to the camera.

4. Nav2 Costmap 2D Server

What it does: Creates a layered cost grid. It overlays rock obstacle coordinates onto the static map and inflates every point with a safety gradient.

Where to use it: Run inside the Nav2 stack as the global_costmap and local_costmap nodes.

How to get it: Installed as part of Nav2: sudo apt install ros-jazzy-navigation2.

How to do it (Brief Implementation): In your Nav2 config yaml, define a static layer (subscribing to `/map`) and an obstacle layer (subscribing to `/perception/obstacles_only`). Specify your rover's footprint size and inflation parameters.

B. Topic & Transform Definitions

  • /wheel/ticks: The raw rotation counts from encoders. Published by the hardware driver; subscribed by the EKF node.
  • /imu/data: Absolute orientation quaternions and angular speeds. Published by the BNO055 IMU driver; subscribed by the EKF.
  • /camera/color/image_raw: Raw video stream. Published by the RealSense driver; subscribed by the ArUco detector and RTAB-Map.
  • /camera/depth/image_rect_raw: Grayscale depth frames. Published by the RealSense driver; subscribed by RTAB-Map to construct map obstacles.
  • /perception/obstacles_only: Bounding box/point coordinates of detected rocks. Published by the Perception terrain node; subscribed by the Costmap 2D Server.
  • /perception/aruco_pose: Fused 6-DOF coordinates of seen markers. Published by the ArUco node; subscribed by RTAB-Map to fix global drift.
  • /odometry/filtered: Fused local coordinates. Published by the EKF node; subscribed by RTAB-Map and the local planner.
  • /global_costmap/costmap: The final inflated occupancy grid. Published by the Costmap 2D Server; subscribed by the A* global planner.
  • odom → base_link transform: The smooth, local translation frame offset. Published by the EKF node at 100 Hz.
  • map → odom transform: The slower, global drift correction transform frame. Published by RTAB-Map at 1–5 Hz.

5. How it Works (Under the Hood)

Step 1: The Local Control Loop (Fast)

As the rover drives, the wheel encoders report rotation speed and the IMU reports turns. The robot_localization EKF processes these numbers almost instantly (100 times a second). It updates the odom $\rightarrow$ base_link transform frame, ensuring the wheels spin smoothly to follow target trajectories.

Step 2: The Global SLAM Loop (Slow)

In the background, RTAB-Map processes heavy camera images at about 15–30 Hz. It builds a mathematical map of rocks and key landmarks. When it recognizes a place it saw before, it calculates how much the rover's local odometry has drifted (e.g., "we drifted 50cm to the right").

Step 3: The Offset Broadcast

Instead of resetting the rover's local coordinates, RTAB-Map changes only the **map $\rightarrow$ odom** offset. This acts like a rubber band that pulls the local map frame back to the global coordinates. The EKF continues providing a smooth, uninterrupted ride, completely unaware of the global adjustment.

6. Why it Fits the ERC Requirements

1. Handles Loose Sand Slip

If the rover gets stuck in a sand dune, the wheels will spin but the camera will see that the rover is stationary. Because we run a separate EKF, we can easily plug in a heuristic slip-check. If a slip is detected, we tell the EKF to ignore the wheels and rely strictly on the IMU and visual loop closures, saving the rover from thinking it flew away.

2. Low Latency for MPPI Controller

The MPPI (Model Predictive Path Integral) controller is extremely sensitive to state lag. If it receives state updates at only 15 Hz from a visual SLAM system, the steering will overcorrect and stutter. The EKF solves this by feeding MPPI with pose updates at a clean 100 Hz.

3. Camera Dust / Sunlight Resiliency

If a gust of wind blows dust onto the RealSense lens or direct sunlight blinds the camera, visual SLAM will stop tracking. In an all-in-one system, this triggers a crash. In Option B, the EKF keeps running on encoders and IMU. The rover can safely execute its backup maneuver or wait for the dust to settle.

7. Core Configuration Template

To implement this setup in ROS 2, configure the robot_localization EKF yaml file as follows to only look at wheels and IMU:

# ekf.yaml Configuration Example
ekf_filter_node:
  ros__parameters:
    frequency: 100
    two_d_mode: true
    publish_tf: true

    # Coordinate Frames
    map_frame: map
    odom_frame: odom
    base_link_frame: base_link
    world_frame: odom  # Crucial: Local EKF only outputs odom -> base_link!

    # Sensor Encoders Input (X, Y velocity)
    odom0: /wheel/odom_raw
    odom0_config: [true,  true,  false,
                   false, false, false,
                   true,  true,  false,
                   false, false, true,
                   false, false, false]

    # IMU Input (Orientation, Angular Velocity)
    imu0: /imu/data
    imu0_config: [false, false, false,
                  false, false, true,  # Yaw
                  false, false, false,
                  false, false, true,  # Angular Z
                  true,  true,  false] # Acceleration

For RTAB-Map, in your launch file, configure publish_tf to true but ensure its world frame is set to map, allowing it to publish the map $\rightarrow$ odom transform link.
