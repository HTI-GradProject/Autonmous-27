Advanced Perception Architecture

RealSense + BNO055 + Jetson Orin Nano Implementation

1. Hardware Context: Jetson Orin Nano 8GB

The Jetson Advantage: The Orin Nano 8GB features an Ampere GPU with 1024 CUDA cores. By building custom C++ nodes, we leverage CUDA acceleration and unified memory to make the rover highly competitive.

2. Role & Requirements

The perception module must execute three core tasks: Detect Obstacles (rocks/craters), Provide Global Odometry (Visual SLAM), and Detect Navigation Markers (ArUco tags).

3. System Inputs

  • RGB Image (sensor_msgs/Image): Standard color video stream.
  • Aligned Depth Data: Depth image where every color pixel is aligned to a physical distance.
  • Camera Intrinsics (CameraInfo): Calibration math to project 2D pixels into 3D space.

4. Pre-Processing Pipeline (Filter Stage)

Raw depth data must be processed via the realsense2_camera driver using Decimation, Spatial, Temporal, and Hole-Filling filters to ensure accuracy and save CPU.

5. The BNO055 IMU Advantage

The Bosch BNO055 has a built-in Cortex-M0 processor that performs sensor fusion internally, outputting perfect, absolute orientation (Quaternions). This eliminates the need for software IMU filters.

6. Phase 1: The "Old Way" (Ready-Made MVP)

This is the standard approach using off-the-shelf ROS packages (e.g., pointcloud_to_laserscan). It requires zero custom coding and serves as our baseline test to ensure the RealSense and BNO055 are publishing correctly before custom development.

8. The 3 Perception Branches Explained

Branch 1: Terrain Geometry & Persistent Memory

This branch processes raw 3D point clouds to find physical barriers and ensures the rover never forgets them.

  • Ingestion & Voxel Downsampling: Millions of points are squashed into a 5cm 3D grid, shrinking data by 90% to prevent the Jetson from crashing.
  • RANSAC Ground Removal: A geometric algorithm mathematically finds the largest flat plane (the Martian dirt) and deletes it, leaving only steep ramps and floating objects.
  • DBSCAN Clustering: Groups the remaining floating points together based on physical proximity into distinct "Clusters" (Rocks).
  • Persistent Memory Node: A custom Python database that receives the 3D bounding boxes. It uses Exponential Moving Average (EMA) to smooth the rock's location. Even if the camera looks away, it keeps broadcasting the rock to the Path Planner.

Branch 2: ArUco Marker Detection (Distance & Angle Math)

This branch uses computer vision to find mission objectives and calculate their exact 3D distance without using the depth sensor.

  • The PnP Math (Perspective-n-Point): By defining the physical size of the printed marker (e.g., 0.2m), the node scans the 2D image for the marker's 4 corners. Using the Camera Intrinsics (lens curvature), it calculates the exact 3D Translation (X, Y, Z distance) and 3D Rotation (Roll, Pitch, Yaw angle) required for a 0.2m square to look like that in the camera frame.
  • Localization Integration:
    • If the absolute global GPS coordinates of the markers are known, feeding this 6-DOF pose into the EKF can instantly wipe out odometry drift.
    • In the ERC, marker coordinates are usually unknown. Therefore, the node simply feeds this distance/angle data to the State Machine (e.g., "Drive 3 meters forward to scan the probe").

Branch 3: Visual SLAM (RTAB-Map Deep Dive)

This branch tracks the rover's movement and builds the infinite 3D map. RTAB-Map runs an incredible continuous loop:

  1. Time Synchronization: Waits to receive the RGB Image, Aligned Depth Image, Camera Intrinsics, and BNO055 IMU Quaternion at the exact same millisecond.
  2. Feature Extraction: Scans the RGB image to find hundreds of highly distinct visual landmarks (e.g., sharp corners of rocks).
  3. Depth Assignment: Cross-references those landmarks with the Aligned Depth image to find their exact X, Y, Z physical distance.
  4. Visual Odometry: As the rover moves, it finds those exact same features in the next frame. By calculating how far those 3D features shifted across the screen, it mathematically proves exactly how far the rover drove.
  5. Graph Building: Saves this movement into a long mathematical chain.
  6. Loop Closure (The Magic Trick): Constantly compares current features against a database of past features. If it recognizes a rock it saw 5 minutes ago, it calculates the drift error and instantly snaps the entire map back into perfect alignment.

10. Implementation Guide: How to Make Each Branch

When it is time to write the actual code for this architecture, here is exactly how each branch will be built:

Building Branch 1: Terrain Geometry & Memory

Terrain Geometry Node (C++): This node processes millions of points, so it must be written in C++ for maximum speed. It will heavily utilize the Point Cloud Library (PCL).
Core Code: pcl::VoxelGrid for downsampling, pcl::SACSegmentation for RANSAC ground removal, and pcl::EuclideanClusterExtraction for DBSCAN clustering.

Persistent Memory Node (Python): Because the heavy 3D math is finished by the C++ node, this node only manages a list of 3D coordinates. It will be written in Python (rclpy) for ease of state-machine tracking. It uses Euclidean distance checks to compare new boxes to known boxes, and applies an Exponential Moving Average (EMA) equation to smooth out camera jitter.

Building Branch 2: ArUco Vision Node

Vision Node (C++): This node processes 1080p images. It will be written in C++ utilizing the OpenCV library (cv_bridge to convert ROS images).
Core Code: It will use cv::aruco::detectMarkers() to locate the squares, and cv::solvePnP() to run the Perspective-n-Point math against the Camera Intrinsics to output the 6-DOF Pose.

Building Branch 3: Visual SLAM

Launch Files (XML/Python): You do not write C++ code for SLAM. The math is incredibly complex and standard packages are already perfected. Building this branch simply requires writing standard ROS 2 Launch files to spin up the rtabmap_ros package, perfectly tuning its YAML parameters (like feature extraction type and memory limits) to match the Jetson's capabilities.
