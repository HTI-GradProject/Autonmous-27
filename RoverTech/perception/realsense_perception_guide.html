1. General Requirements

1. What is Required from a Rover Perception Module?

A rover's perception module acts as its eyes and spatial brain. Its core job is to convert raw physical values (light, depth, acceleration) into a meaningful model of the surrounding world that the path planners and mechanical arms can interact with.

Core Requirements:

  • Bandwidth Regulation (The Sizing Problem): Depth cameras capture huge amounts of data. Streaming raw 1280x720 video at 30 FPS saturates USB buses and overheats processors like the Jetson Orin Nano. The module must regulate this stream, downscaling to manageable frames (like 640x480 at 15 FPS) based on compute capacity.
  • Sensor-Level Denoising: Active stereoscopic depth cameras produce messy depth data with jagged outlines, flickering pixels, and hollow black "holes" where calculation failed. The module must actively filter this stream to avoid publishing phantom rocks or fake craters.
  • Spatial Coordinate Alignment: Because the RGB color lens and the depth sensors are physically separated by a few centimeters on the camera, their coordinate fields are mismatched. The module must warp and reproject the depth frame to align pixel-for-pixel with the color frame.
  • Strict Hardware Time Synchronization: Different sensors run at different speeds (IMU at 200 Hz, Encoders at 50 Hz, Camera at 15 Hz). If a camera frame from 2 seconds ago is processed as if it happened now, the rover will crash. The module must strictly timestamp all incoming frames to synchronize them.

2. Deep-Dive: Output Messages & Variables

Robotic controllers don't understand "pictures." They communicate through structured ROS 2 message matrices. Here is a deep explanation of each output type, its variables, who uses them, and concrete examples.

1. 2D / 2.5D Local Costmaps (nav_msgs/msg/OccupancyGrid)

What it is: A flat grid map representation where the world is divided into grid cells. Each cell contains a single value representing the confidence of an obstacle sitting at those coordinates.

Variable Name Data Type What it actually means (Simply Explained)
info.resolution float32 The size of one grid cell in meters (e.g. 0.05 means each grid square represents a 5cm x 5cm patch of sand).
info.width / height uint32 The size of the map in cells (e.g. 100 x 100 cells with a resolution of 0.05m creates a 5m x 5m grid).
info.origin Pose The starting coordinate (X,Y) of the bottom-left corner of the grid relative to the center of the rover.
data int8[] A flat list of numbers (values from 0 to 100). 0 = completely empty sand, 100 = a certain obstacle (like a boulder), and -1 = unknown/unexplored space.

Used by: The **Nav2 Controller** (DWA or TEB local planners) to steer wheels around obstacles.

Visual Map Representation:
# Legend: [R] = Rover (center), [.] = Free Sand (0), [X] = Boulder (100), [?] = Unknown (-1) [?] [?] [?] [?] [?] [?] [?] [?] [?] [?] [.] [.] [.] [.] [.] [.] [.] [?] [?] [.] [X] [X] [.] [.] [.] [.] [?] <-- Row contains '100' at the boulder coordinates [?] [.] [.] [.] [.] [.] [.] [.] [?] [?] [.] [.] [.] [R] [.] [.] [.] [?] <-- Rover sits at center origin (0, 0) [?] [.] [.] [.] [.] [.] [.] [.] [?]

Concrete Example: If the rover stands 1m directly in front of a rock, the costmap node calculates that the cell at offset +1.0m on the X-axis corresponds to index 5020 in the data array and writes the value 100 (obstacle) to it.

2. 3D Point Clouds (sensor_msgs/msg/PointCloud2)

What it is: A massive list of 3D spatial points (X,Y,Z) outlining coordinates of surfaces in front of the camera.

Variable Name Data Type What it actually means (Simply Explained)
fields PointField[] Describes what data is inside each point (usually x, y, z representing coordinates, and rgb or intensity values).
data uint8[] The actual binary block containing the coordinates of the points. Every set of 16 or 32 bytes contains the binary representation of a single 3D point.
is_dense bool True if there are no invalid/NaN values (where matching failed) in the data array.

Used by: The **Robotic Arm Planner (MoveIt)** to prevent arm joints from colliding with the ground, chassis, or nearby structures.

Point Cloud Visual Schema:
Point # X (Forward in m) Y (Left/Right in m) Z (Height in m) Intensity (surface reflection)
Point 1 (Ground) 1.25 0.12 -0.32 0.45
Point 2 (Obstacle tip) 1.54 -0.45 0.24 0.89

Concrete Example: When YOLO detects a panel, MoveIt! looks at the PointCloud points sitting inside the bounding box. It extracts the coordinate [X: 1.54, Y: -0.45, Z: 0.24] relative to the arm mount, telling the arm: "Drive the end-effector exactly to this physical point."

3. 6-DoF Landmark Poses (geometry_msgs/msg/PoseStamped)

What it is: A single coordinate point in space indicating the location and orientation of a target (like an ArUco marker) relative to a specific reference frame.

Variable Name Data Type What it actually means (Simply Explained)
header.frame_id string The frame of reference this pose is calculated in (e.g. base_link or camera_color_optical_frame).
pose.position Point (x, y, z) The distance from the origin in meters. X = forward/back, Y = left/right, and Z = up/down.
pose.orientation Quaternion (x, y, z, w) A set of four numbers representing rotation in 3D space to avoid "Gimbal Lock" (where coordinate axes align and freeze).

Used by: The **Robotic Arm Inverse Kinematics (IK)** solver to align and interact with panels, and the **SLAM Localization** node to reduce positioning drift.

Rotation & Orientation Analogy:

Think of your hand. Its position (X, Y, Z) tells you where your wrist is, but to turn a key or switch, you must tilt your hand. The orientation quaternion describes this tilt: **Roll** (tilt left/right), **Pitch** (tilt up/down), and **Yaw** (spin left/right).

Concrete Example: An ArUco tag on the lander panel is detected. The node publishes:
position: [x: 1.45, y: -0.10, z: 0.05] (Tag is 1.45m ahead of camera, 10cm to the right, and 5cm up).
orientation: [x: 0.0, y: 0.707, z: 0.0, w: 0.707] (This quaternion represents a pitch tilt of exactly 90 degrees, indicating the panel is vertical).

4. Visual Odometry Estimates (nav_msgs/msg/Odometry)

What it is: A compound message showing how far the rover has driven and how fast it is moving, along with the system's confidence in those readings.

Variable Name Data Type What it actually means (Simply Explained)
pose.pose Pose The estimated 3D position (X, Y, Z) and orientation of the rover relative to its start point.
pose.covariance float64[36] A grid indicating the system's uncertainty. Small numbers mean high certainty; large numbers mean the estimates are drifting or unreliable.
twist.twist Twist The speed of the rover, split into linear velocity (vx, vy, vz in m/s) and angular speed (vyaw in rad/s).

Used by: The **robot_localization EKF Filter** node to merge wheel encoders and visual positioning.

The "Covariance Bubble" Analogy:

Imagine walking in a dark hallway. If you walk 3 steps, you are highly certain of your position (small covariance). If you walk 50 steps without looking, your uncertainty grows (large covariance bubble). The EKF uses these numbers to decide whether to trust the camera or the wheel encoders during sand drifts.

Concrete Example: As the rover rolls over rocks, the visual tracker outputs a linear speed of 0.2 m/s along the X-axis (forward) with a small covariance of 0.02. If dust blocks the camera lens, the tracking node detects feature loss and increases the covariance value to 0.85 (meaning "I am drifting and unsure"), telling the EKF to ignore the camera and trust the wheel encoders instead.

3. How is the Perception Module Structured?

The perception pipeline runs sequentially. It takes camera inputs, cleans them, removes self-reflections, and then splits into three independent, parallel processing branches to compute localization, terrain models, and marker poses.

Pipeline Architecture Structure
  [ Raw Left/Right Video + IMU ]  <-- USB 3.0 Handshake
               │
               ▼
   [ Rectification & Alignment ]  <-- Align Depth pixel-for-pixel with Color
               │
               ▼
   [ Crop Box Self-Filtering ]    <-- Erase points falling on the Rover chassis
               │
      ┌────────┴────────┬────────┐
      ▼                 ▼        ▼
  [Branch A]        [Branch B]   [Branch C]
  Terrain Geometry   Fiducials    Visual Tracking
      │                 │        (ORB Features)
  RANSAC Ground     Grayscale           │
      │             Threshold       Motion Estimation
  Voxel Grid            │               │
      │             Quad Warp      Sensor Fusion EKF
  DBSCAN Cluster        │               │
      │             solvePnP            │
      ▼                 ▼               ▼
[Costmap Output]   [6-DoF Pose]    [Fused Odometry]

4. Pipeline Branches & Steps to Implement Each

This section outlines the steps to build each processing branch from the ground up, detailing what the algorithms do in simple terms.

Route 1: Ingestion & Depth-to-Color Alignment

What it does: Establishes a hardware connection to the camera, corrects lens distortion, and aligns the depth coordinates to match color pixels.

Implementation Steps:
  1. Configure the camera frame rate to 15 FPS at 640x480 resolution to conserve Jetson compute.
  2. Read calibration matrices (focal length, baseline offset) from the camera's internal memory.
  3. Remap/rectify raw images so left and right stereo images align perfectly on the same pixel rows.
  4. Calculate the coordinate offset (extrinsics) to warp the depth map onto the color grid.

Route 2: Terrain Geometry & Obstacle Detection

What it does: Crops the robot chassis out of the point cloud, isolates the ground, downsamples, and clusters hazards.

How the algorithms work (Simply Explained):
  • CropBox Self-Filter: Draws a virtual 3D box around the rover coordinates and discards any points inside to prevent the rover from seeing its own tires or arm.
  • RANSAC Ground Plane Removal: Fits a flat mathematical plane to the point cloud. Points on this plane are labeled "Ground" and removed, leaving only hazards sticking up.
  • Voxel Grid Downsampling: Divides space into cubes (voxels) and averages points inside each voxel to reduce point cloud density by 90%.
  • Euclidean / DBSCAN Clustering: Groups remaining points that sit close to each other, labeling each group as a distinct hazard (rock or crater).

Route 3: Fiducial Tags & Marker Detection

What it does: Finds printed ArUco tags, decodes their ID, and calculates their relative distance and rotation.

How the algorithms work (Simply Explained):
  • Adaptive Thresholding: Converts the frame to high-contrast black and white to isolate tag borders.
  • Homography Warp: Corrects perspective skew. If a tag is viewed from the side, it looks like a trapezoid; this warp stretches it back to a flat 2D square.
  • solvePnP: Perspective-n-Point. Since the tag has a known physical size (e.g. 15cm), solvePnP measures the pixel coordinates of the corners to calculate the tag's exact 3D distance and rotation.

Route 4: Visual Tracking & Sensor Fusion

What it does: Tracks rover motion via the camera and fuses it with wheel encoders to output drift-corrected odometry.

How the algorithms work (Simply Explained):
  • ORB Keypoint Tracking: Tracks visual landmark points (e.g. rock corners) across sequential frames. If points shift backward, the rover is moving forward.
  • EKF Sensor Fusion (Extended Kalman Filter): Blends the camera's visual odometry with wheel encoders. If wheels spin in loose sand, the EKF filters out the slip to maintain an accurate position estimate.

5. Ready-Made Packages & Sizing

Do not write these complex algorithms from scratch. Instead, build your perception system by configuring ready-made open-source ROS 2 packages:

1. For Camera Ingestion & Alignment

Use **`realsense2_camera`** or **`zed_wrapper`**.

How to do it: Set launch flags to enable depth-color alignment and IMU interpolation:

ros2 launch realsense2_camera rs_launch.py align_depth.enable:=true enable_gyro:=true enable_accel:=true unite_imu_method:=2

2. For Chassis Self-Filtering

Use **`sensor_filters`**.

How to do it: Configure a `CropBox` filter node to crop out coordinates within your rover's physical dimensions (e.g., $X \in [-0.5, 0.5]$ meters).

3. For Terrain Mapping & Obstacle Costmaps

Use the standard **`Nav2 Obstacle Layer` / `Voxel Layer`**.

How to do it: Configure Nav2 parameter files (`nav2_params.yaml`) to subscribe to the point cloud topic. Nav2 has built-in parameters to filter ground planes and mark obstacles automatically.

4. For Fiducial Tags (ArUco Detection)

Use the open-source **`ros2_aruco`** package.

How to do it: Specify the topic inputs (rectified color image + camera info), the printed marker size in meters (e.g. `0.15`), and dictionary lookup parameters.

5. For Sensor Fusion (Visual Odom + Wheel Encoders)

Use **`robot_localization` (EKF)**.

How to do it: Set up the EKF yaml configuration to read absolute pose from your camera's visual odometry and linear velocity from wheel encoders to publish a unified `/odom` coordinate frame.
