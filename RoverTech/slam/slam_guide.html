SLAM Module Architecture

1. Overall Inputs, Flow, and Outputs

System Overview

The SLAM module acts as the rover's memory. It consumes the clean data output by the Perception Module, fuses it mathematically, and outputs the exact Global Map and the exact Rover Position within that map.

What does this mean?

  • Overall Inputs: The SLAM module consumes raw hardware data (Wheels/IMU) and three cleaned outputs from the Perception Module (Rocks, Camera Odometry, ArUco Tags).
  • Overall Outputs: It produces exactly two things: /odometry/filtered (where the rover is) and /map (where the obstacles are). The Path Planner needs both to drive safely.

2. The Fuzzy Inference System (FIS)

A Kalman Filter uses two fundamental matrices to represent its "trust" in the sensors:

  • Q Matrix (Process Noise): Represents how much we distrust our internal predictions (the Wheels and IMU).
  • R Matrix (Observation Noise): Represents how much we distrust our external measurements (the Camera).

Normally, these are hard-coded in a YAML file. In your advanced architecture, the FIS dynamically calculates them on every single frame.

Rule 1: Evaluating the Camera (R Matrix / Observation Noise)

  • Inputs Analyzed: ORB Keypoint Number (K) & ORB Reprojection Error (E).
  • Fuzzy Logic: If the camera sees very few keypoints (staring at flat sand) OR the reprojection error is high (image is blurry/shaking), the FIS increases the R Matrix.
  • Result: The filter is told "The camera is blind right now, ignore it and trust the wheels."

Rule 2: Evaluating the Wheels (Q Matrix / Process Noise)

  • Inputs Analyzed: Wheel Velocity Difference (Slip), Z-Axis Angular Velocity, X-Axis Linear Velocity.
  • Fuzzy Logic: If the wheels are spinning at vastly different speeds but the IMU detects no physical rotation, the wheels are slipping in a sand trap. The FIS increases the Q Matrix.
  • Result: The filter is told "The wheels are slipping and lying to you, ignore them and trust the camera."

Is there a ready-made package for this?

No. The Fuzzy Inference System is a highly custom, academic-level architecture. To implement this exactly, you must write a custom ROS 2 Python Node that uses the scikit-fuzzy library to calculate the rules and publish the dynamically changing Q and R matrices to your Kalman Filter.

3. Odometry Fusion System (IESKF)

With the Trust (Covariance) matrices actively updated by the FIS, the Iterated Extended Kalman Filter can safely fuse the data streams.

Step 1: Predict Phase (Wheel-Inertial Odometry)

The IMU provides absolute Orientation. The Wheel Encoders provide Linear Velocity. Together, they form the WIO. The IESKF uses the WIO to mathematically "Predict" where the rover moved in the last 10 milliseconds. (This prediction is governed by the Q Matrix).

Step 2: Observe Phase (Wheel-Visual Odometry)

The ZED Camera (Perception Branch 3) calculates interframe movement using ORB tracking. The IESKF takes this measurement and compares it against its guess. It uses the dynamic Q and R matrices to weigh which sensor is currently more reliable, calculates the error, and outputs the highly accurate, finalized Odometry.

Step 3: Global Correction (ArUco Reset)

Even the best EKF will slowly drift over time. If Perception Branch 2 detects an ArUco marker, it feeds this into the IESKF. Because the ArUco marker is a known ground-truth anchor in the arena, the IESKF performs a hard "Error Reset", instantly zeroing out any accumulated drift.

Is there a ready-made package for the EKF? (The Easier Way)

Yes. If you do not want to build a Kalman Filter from scratch, you can use the industry-standard ROS 2 package robot_localization.

  • How it works: It provides a highly optimized, ready-made EKF node. You just write a YAML file telling it to listen to your Wheel Odometry, IMU, and Visual Odometry topics.
  • The Catch: It does not support the dynamic Fuzzy Logic matrices. The covariance matrices are hard-coded in the YAML file. If the wheels slip in sand, the standard EKF will not dynamically adjust its trust, and the odometry will drift.
  • Recommendation: Start with robot_localization to get the rover moving. Once the basic pipeline works, swap it out for your custom Fuzzy IESKF for competition-level accuracy.

4. The Mapping Module

The Mapping Module is responsible for drawing the 2D Occupancy Grid that the Global Path Planner will use to navigate the Mars Yard.

  • It receives the perfectly fused /odometry/filtered from the IESKF. This tells the map exactly where the robot is.
  • It receives the /perception/obstacles_only (the clean rock coordinates from Perception Branch 1).
  • Because Perception Branch 1 already used RANSAC to remove the sand, the Mapping Module does not need to worry about filtering ground noise. It simply stamps the incoming rocks onto the 2D grid at the exact coordinates provided by the IESKF.

Is there a ready-made package for Mapping? (The Easier Way)

Yes, absolutely. You do not need to write custom mapping code. The industry-standard package is slam_toolbox.

  • How it works: You configure it via YAML. You tell it to listen to your `/odometry/filtered` topic and your Branch 1 point cloud. It will automatically stitch the rocks onto a 2D Occupancy Grid and publish the final `/map` topic.
  • Recommendation: Use slam_toolbox. Writing a custom mapping node is extremely complex and unnecessary, as `slam_toolbox` is already highly optimized in C++ for lifelong mapping and loop closure.
